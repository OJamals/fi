# Agent Note: credential-reference resolution for the Exa and Perplexity search providers

Status: implemented

English | [中文](2026-09-25-web-search-exa-perplexity-credential-reference.zh.md)

## Problem

`dsh-web-search-exa` and `dsh-web-search-perplexity` captured their API key once, at plugin registration: `apply()` read `config.apiKey ?? launchEnvironmentOf(ctx).get('EXA_API_KEY')?.value ?? ''` (respectively `PERPLEXITY_API_KEY`) into a fixed options object handed to the provider's constructor. A key stored or rotated through `ctx.credentials` after that point had no effect until the plugin reloaded, and a deployment with no key at registration time saw the generic `WEB_PROVIDER_CONFIGURED_UNAVAILABLE` from the `ctx.web` registry rather than a diagnosis naming the missing credential reference. `dsh-web-search-deepseek` had already solved both problems for itself — `resolveApiKey`/`apiKeyEnv` on a thunk-supplied options object, re-resolved fresh on every search, with a `WEB_PROVIDER_CREDENTIAL_MISSING` error naming the reference and where to store it — but the other two providers never received the same treatment, an asymmetry with no remaining justification.

Independently, `@fi/web-search-preferences` — the router this repository actually ships (`packages/fi/authorization-bundle/cordis.patch.yml`) — already resolves the credential fresh for every operation itself, external to these packages, and constructs a new provider instance per search. So the gap was real for the two packages' own standalone `apply()`/`Config` (published surface a deployment can mount directly, per each package's `peerDependencies`), not for fi's shipped web-search path.

## Decision

`ExaSearchProvider` and `PerplexitySearchProvider` take a `resolveOptions: () => Options` thunk instead of a fixed options object, matching `DeepSeekSearchProvider`'s constructor exactly. `available()` and `search()` call the thunk once per operation; `search()` additionally resolves the API key through a new private `apiKey()` method: a non-empty `options.apiKey` wins outright, otherwise `options.resolveApiKey()` is awaited under the caller's `AbortSignal` (via the same `abortable`/`throwIfSearchAborted`/`searchAborted` helpers `DeepSeekSearchProvider` already uses), and an unresolved key throws `WEB_PROVIDER_CREDENTIAL_MISSING` naming `options.apiKeyEnv` and where to store it. Each package's `Config` gained `apiKeyEnv` (a `credential-ref`-rolled string defaulting to the provider's own env var name) alongside the existing `apiKey`; `apply()` builds a `resolveOptions(ctx, config)` closure that reads the credential through `ctx.get('credentials')` when mounted, falling back to `launchEnvironmentOf(ctx)` otherwise — byte-for-byte the same fallback DeepSeek's `resolveOptions` already performs.

Both packages' `Config` fields stay plain (non-`Volatile`) rather than adopting DeepSeek's reactive-settings shape: nothing consumes a live Exa/Perplexity settings section today (`ui-settings-web-search` is hardcoded to the `web-search-deepseek` namespace), so `Volatile` fields and a settings card for these two providers would be unused machinery. The thunk still buys the credential-rotation behavior on its own, because `resolveApiKey` performs a fresh `ctx.credentials.resolve()` on every call regardless of whether the surrounding `Config` is reactive.

`@fi/web-search-preferences` already resolves the credential itself and rebuilds the provider per operation, so its two call sites change only to wrap their already-resolved options in `() => options` — the constructor's thunk is invoked at most once there, and behavior is unchanged.

The near-identical `resolveApiKey` closure (index.ts), the `apiKey()` method, and the `if (!response.ok)` HTTP-error-parsing block are now duplicated verbatim (or near-verbatim) across the three web-search-* provider packages; each occurrence in `web-search-exa`/`web-search-perplexity` carries a bare `/* jscpd:ignore-start */…/* jscpd:ignore-end */` pair (the exact string `jscpd.json`'s `ignorePattern` matches — explanatory prose must sit in an adjacent comment, not inside the marker comment itself, or the pattern silently fails to match). `web-search-deepseek` is left unmarked: excluding only the exa/perplexity occurrences from jscpd's corpus already leaves no duplicate pair to report.

## Alternatives considered

- **Route Exa/Perplexity's standalone `apply()` through `@fi/web-search-preferences`'s `resolveCredential()` instead of duplicating DeepSeek's pattern.** Rejected: that router is an `@fi/*` package one layer above these two published `@deepseek-ai/dsh-web-search-*` packages; making the providers depend on it would invert the dependency direction and couple an upstream-shaped package to an fi-specific consumer.
- **Give Exa/Perplexity the full `Volatile` config surface DeepSeek has.** Rejected for now: no settings UI reads a live Exa/Perplexity section, so the reactivity would have no observable effect and would add unused config-schema machinery. Revisit if/when `ui-settings-web-search` (or a successor) generalizes beyond the `web-search-deepseek` namespace.
- **Leave the standalone packages as-is, since fi's shipped router already covers the credential-rotation problem in production.** Rejected: these packages are published (`publishConfig.access: public`) and importable independent of the router; a deployment or downstream project that mounts `web-search-exa`/`web-search-perplexity` directly hits the exact bug `web-search-deepseek` already fixed for itself.

## Consequences

`ExaSearchProvider`/`PerplexitySearchProvider`'s constructor is a breaking change for any direct instantiation with a plain options object; the two call sites in this repository (`@fi/web-search-preferences`, plus each package's own tests and `*.e2e.ts` smokes) are updated in the same change. Both packages gained a `@deepseek-ai/dsh-credentials` peer/dev dependency and Exa/Perplexity's devDependencies gained `@deepseek-ai/dsh-credentials-local` for the rotation test. `is unavailable when neither config nor env supplies a key` (`WEB_PROVIDER_CONFIGURED_UNAVAILABLE`, checked at the `ctx.web` registry before `search()` runs) is gone from both test suites: `available()` now returns `true` whenever a `resolveApiKey` thunk exists (it always does, once `apply()` runs), so the diagnosis moves into `search()` itself as `WEB_PROVIDER_CREDENTIAL_MISSING` — a strictly more specific error, matching `web-search-deepseek`. Deferred: a settings card generalized across all `ctx.web` providers (today `ui-settings-web-search` names only `web-search-deepseek`), and extracting the now-tripled `resolveApiKey`/`apiKey()`/HTTP-error-parsing shape into a shared helper, deliberately left as jscpd-marked duplication until a fourth provider or a real behavioral divergence forces the extraction.
