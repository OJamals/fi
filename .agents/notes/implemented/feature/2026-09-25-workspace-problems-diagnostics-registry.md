# Agent Note: Workspace diagnostics registry (`ctx.problems`) and its model tool

Status: implemented

English | [中文](2026-09-25-workspace-problems-diagnostics-registry.zh.md)

## Problem

An older, since-superseded GUI line (`codex/model-universal`) built a coding-controller subsystem: a diagnostics registry, a project task runner with pass/fail verification and run history, model tools over both, a browser BFF, and a five-column-workbench client UI. An audit for this fork found no equivalent capability on `main`: `packages/lsp` deliberately excludes diagnostics from its read-only navigation tool, `packages/jobs` runs arbitrary background commands with no diagnostic-source concept, and `packages/goal`/`packages/schedule`/`packages/workflow` track objectives, follow-ups, and multi-phase runs, none of which is a diagnostics registry. A model or a future producer (a lint runner, a task-failure parser, an LSP diagnostics forward) has nowhere to publish structured diagnostics for a Workspace, and no tool to read them back.

## Decision

Ported the registry and its Consumer from the superseded branch, adapted to this fork's current conventions, as two packages: [`packages/core/problems`](../../../../packages/core/problems/README.md) (`ctx.problems`) and [`packages/core/tool-problems`](../../../../packages/core/tool-problems/README.md) (the `problems` tool). `Problems` keeps one source map per canonical Workspace root; a producer calls `replace(workspaceRoot, source, problems)` with its complete current contribution (empty clears it), and `inspect()`/`subscribe()` give consumers a detached, deterministically ordered snapshot (severity, path, position, source, code, message) that only advances its `revision` when visible content actually changed. `dsh-tool-problems` derives the Workspace from the calling agent's Session, resolves it through `ctx.fs`, and renders a bounded, truncation-marked result; a new `TOOL_PROBLEMS` system-prompt section order (2500, between `TOOL_GOAL` and `TOOL_WORKFLOW`) carries its one stable guidance line.

Both packages ship as available, opt-in capabilities — like `dsh-lsp`/`dsh-tool-lsp`, neither is mounted in any shipped bundle (`dsh-base`, `dsh-web-app`, `dsh-headless`, `dsh-sdk-app`, `dsh-acp-app`) by default, so this change touches no keyless recorded-session snapshot. No producer ships in this change either: `problems` is a complete two-role seam (Service Definition/Provider combined in `dsh-problems`, Consumer in `dsh-tool-problems`) that returns "none" until a deployment mounts a producer, exactly as its own Model Experience section documents.

## Alternatives considered

**Port the full coding-controller subsystem (task runner, task verification, tool-tasks, the browser BFF, the client workbench)** — rejected for this change. The superseded branch's client packages (`client/ui-problems`, `client/ui-tasks`) register into a `workbench` slot family and call `ctx.layout.openWorkbench(...)`; `main`'s current `dsh-client-ui-layout` is a three-column `AppFrame` with no `workbench` slot or `openWorkbench` method anywhere in the tree, so that UI cannot be ported without redesigning it against `dsh-client-ui-dockkit`/the sidebar system — a separate, larger effort. The task runner's local provider (`jobs/task-runner-local`) is written against the old branch's `ctx.jobs`; `main`'s current `JobRegistry.start(spec: JobSpec)` (pull `output` sources, a `run(job): JobHooks` starter, `owner: SessionId` rather than a live `Agent`) is a different shape, and the task runner also needs Git-revision observation, diagnostic parsing, and a session-log run-history projection — enough new design surface to deserve its own scoped PR rather than being bundled here under the "keep scope tight" instruction. Porting only the registry and its reader avoids all of that while still closing the diagnostics half of the gap.

**Wire a producer in the same change (e.g. forward `dsh-lsp-stdio`'s diagnostics notifications into `ctx.problems`)** — rejected for this change: `dsh-lsp`'s Service Definition deliberately excludes diagnostics from its request/response vocabulary, so wiring one through would mean widening that seam's contract, which is out of scope for adding the registry itself. The registry is deliberately useful with zero producers mounted, which is what its `problems` tool result already documents.

**Register `dsh-problems`/`dsh-tool-problems` into `dsh-base` by default** — rejected: nothing in this fork feeds the registry yet, so a mounted-by-default `problems` tool would only ever answer "none," which is a real answer but not obviously more useful than the tool not existing at all. Leaving both unmounted (like `dsh-lsp`/`dsh-tool-lsp`, which also require external configuration before they matter) keeps this an available capability a future producer can pair with, without inflating every shipped agent's tool count or touching any snapshot fixture today.

## Consequences

A future diagnostics producer (a lint runner, a task-failure parser, an LSP forward) has one canonical place to publish structured, bounded diagnostics per Workspace, and one canonical model tool to read them back; neither package needs to change when that producer arrives. The Known Limitations sections of both READMEs state plainly that no shipped producer exists yet, so a reader does not mistake "the tool answers none" for "the Workspace has no diagnostics." The task-runner/task-verification/tool-tasks/coding-controller/client-workbench half of the original subsystem remains unported; a future change that wants project-task execution with verification needs its own Agent Note against `main`'s current `ctx.jobs` shape and session-projection seam, and its own decision about whether the workbench UI is worth rebuilding on `dsh-client-ui-dockkit` or should stay host/tool-only.

## Required verification

Unit tests cover the registry's atomic replace/inspect/subscribe semantics, its per-source and per-Workspace bounds, and listener isolation, in [`packages/core/problems/tests/problems.spec.ts`](../../../../packages/core/problems/tests/problems.spec.ts). The tool's registration, prompt section, Workspace-cwd derivation (including alias resolution through a stubbed `ctx.fs`), rendering order, truncation, and the no-Session-Workspace failure are covered in [`packages/core/tool-problems/tests/tool-problems.spec.ts`](../../../../packages/core/tool-problems/tests/tool-problems.spec.ts). The new `TOOL_PROBLEMS` section-order constant is covered by the existing uniqueness/spacing assertion in [`packages/core/system-prompt/tests/system-prompt.spec.ts`](../../../../packages/core/system-prompt/tests/system-prompt.spec.ts).
