# Agent Note: Managed worktrees and guarded file restore

Status: implemented

English | [中文](2026-09-25-managed-worktrees-and-guarded-file-restore.zh.md)

## Problem

A coding session that runs directly in a Workspace's own directory changes the user's checkout before the user has reviewed the work: there is no isolation, and no way to undo one turn's edit to one file short of the user's own `git` fluency. An older, divergent GUI branch (`codex/model-universal`, since abandoned in favor of the current architecture) built both capabilities together — application-managed local Git worktrees, and exact-byte "file checkpoints" captured around every tool call inside them — directly inside its own `workspace-controller` package, with a parallel content-addressed blob store (`file-checkpoints.ts`, `checkpoint-storage.ts`) independent of that branch's per-turn changed-files feature. That branch's architecture has since been superseded on `main`: `main` grew `dsh-workspace-changes`, which already takes git working-tree snapshots at every turn's start and end (plus whole-file captures around file-tool edits) for the changed-files card, and `dsh-workspace`/`dsh-api-workspace-controller`, which already own Workspace registration, navigation, and a `workspace/session-activity` activity-check seam. Porting the old branch's file-checkpoint half verbatim would install a second full-worktree-content snapshot mechanism beside one that already exists, capturing overlapping content through a separate code path.

## Decision

**Managed worktrees** are a new capability on `dsh-api-workspace-controller`, configured with an optional `managedWorktrees` block. [`ManagedWorktrees`](../../../../packages/api/workspace-controller/src/managed-worktrees.ts) creates a local Git worktree of a registered Workspace's directory — which must be a local repository root with a committed HEAD — on a fresh branch, from that HEAD alone; uncommitted, staged, and untracked source files are never copied. The new checkout is registered as an ordinary Workspace through the same `WorkspaceRegistry.create` every other Workspace uses, so Session cwd, tool execution, search, and Git inspection keep their existing, single authority, and the existing Workspace sidebar, ordering, and archiving surface the checkout with no separate browser. Application ownership of a checkout is resolved from the checkout's own path shape (`<uuid>/files`, under the configured `managedWorktreeDirectory`) plus a manifest colocated beside it — never inside it, so `git worktree remove` deleting the checkout can never delete the record, and never from a caller-supplied identity, so a client cannot forge managed status by constructing a request. `removeManaged` refuses while any of the Workspace's Sessions reports running work through the `workspace/session-activity` waterfall `dsh-workspace` already declares (the same seam `archiveSession` uses, now reused rather than a second, narrower agent-and-job-only check), and refuses while the checkout has uncommitted, untracked, or ignored content, or commits not yet reachable from its source's current HEAD — nothing unique to the checkout is ever discarded. Git for worktree creation, removal, and status runs with repository hooks, the filesystem watcher, and (for `status`/`worktree` commands) every clean/smudge/process content filter disabled, so a snapshot or mutation never runs arbitrary repository-configured execution.

**File restore** extends `dsh-workspace-changes` instead of adding a second capture mechanism. `WorkspaceChanges.restore(sessionId, seq, index, side, signal)` writes a listed file's already-captured turn-start (`'before'`) or turn-end (`'after'`) content back to its live path — deleting the path when that side was absent — reusing the exact snapshot trees and whole-file captures the package already keeps for the changed-files card. The write is guarded: it reads the live file first and compares it against the *opposite* side, refusing with `diverged` unless the live content still matches exactly, so an edit this summary never observed (a later turn, a manual save, an external process) is never silently discarded. A binary or oversized side refuses the same way `diff` already reports it. The Web route `POST /api/changes.restore` and a button on the existing changed-files card expose it; no new package, no new durable event, and no new capture pass were added. Restore is not scoped to managed worktrees: the data it writes back is exactly what the existing card already shows the user in every session with a repository, so restricting it to managed worktrees would be a product-only restriction with no matching safety property in this architecture.

## Alternatives considered

**Port the old branch's exact-byte, tool-call-interval checkpoint system verbatim.** It captures the complete tracked-and-untracked file set (respecting `.gitignore`) as SHA-256-addressed blobs around every top-level tool call, independent of `dsh-workspace-changes`'s own turn-boundary git-tree snapshots of the same content. Running both inside one managed-worktree session means two independent full-worktree-content capture passes on every tool call, maintained as two unrelated systems. Rejected: it duplicates the snapshot infrastructure this repository already ships and maintains, for granularity (per tool call vs. per turn) this task's scope does not require.

**Give managed worktrees their own durable registry package, mirroring `dsh-workspace`'s registry/controller split.** Rejected because registering a checkout as an ordinary Workspace already gives it every registry behavior (ordering, archiving, deletion) other Workspaces have; a second registry would duplicate that state and require reconciling two sources of truth for one directory. Ownership instead lives beside the checkout as a plain file, exactly as the (superseded) old branch had already decided, because that shipped precedent stayed sound: the checkout's own path is a fact `git worktree remove` cannot silently orphan.

**Hardcode the removal activity check against the Agent and job registries, as the old branch did.** Rejected because `dsh-workspace` already generalizes this exact question — "does this session still have running work" — behind the `workspace/session-activity` waterfall, whose shipped providers also cover subagents and schedules that a hardcoded agent-and-job check would miss. Reusing the existing seam is both less code and strictly more complete.

**Scope `restore` to managed-worktree Sessions only, matching the old branch's product boundary.** Rejected because the old branch's caution was about copying a user's *uncommitted* source files into a new checkout, not about showing or reversing content the changed-files card already displays in every session. There is no additional risk in an ordinary Workspace that the divergence guard does not already cover.

## Consequences

A managed worktree is an ordinary Workspace everywhere except its lifecycle: creation and safety-checked removal. Removing one deletes its registration and its checkout files together but retains its branch and every Session log, so history is never lost, while a Session whose cwd was the removed checkout cannot continue there. Managed worktrees require a local `fs` and `subprocess` execution world; a remote or sandboxed execution world leaves the feature unavailable even when configured. Restore does not serialize with an in-flight turn on the same path — the pre-write divergence check makes an unnoticed clobber unlikely, not impossible against a concurrent tool edit — and it appends no session event and creates no new turn record, so a later turn's own card is unaware a restore happened until its own snapshot runs. Web browser-snapshot and keyless recorded-session evidence for the new UI surfaces were not recorded in this change (no API key and no interactive browser session were available); the focused unit coverage under `packages/api/workspace-controller/tests` and `packages/deliverables/workspace-changes/tests` is the verification this change carries, and a snapshot pass remains outstanding.
