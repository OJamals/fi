# Agent Note: 订阅媒体使用持久化 Harness 附件

Status: implemented

[English](2026-09-11-subscription-media-output.md) | 中文

## 问题

订阅提供方暴露不同的图片生成协议，而会话需要统一的持久化表示来支持展示、后续请求和回放。将提供方 URL 或 base64 当作普通文本返回，会失去附件授权，并可能在模型历史中保留过大的数据。若适配器无法在助手消息中表示图片，生成的图片还可能导致后续请求失败。

## 决定

订阅媒体使用现有的 `ImageBlock`、附件服务和紧凑助手流。提供方特有的图片生成逻辑属于 FI 提供方代码和面向模型的工具，不属于 agent loop（智能体循环）或新的 Session 格式。生成的图片字节先通过附件准入，再由结果暴露持久化引用；原生助手图片和工具结果图片使用现有的会话授权与图库组件。

输入图片保留[规范化附件与确定性请求流水线](2026-08-20-unified-image-request-pipeline.zh.md)。输入文件保留原生 Harness 规则：日志存储结构化文件引用，请求组装为每个提供方将其投影成确定性的只读文件句柄。auth2api 的原生文档和文件上传端点不取代此规则。

原生提供方签名要求使用提供方签署的字节及部分顺序。图片规范化是独立的展示操作：当规范化可能改变这些字节时，已签名原件需要持久化原样存储，而私有回放元数据携带引用而非 base64。若适配器的助手协议消息无法携带图片，则使用显式、保留身份的文本表示该历史；它不会伪造用户消息，也不会声称已发送被省略的像素。

图片生成能力与图片输入相互独立。没有光栅图片生成端点的提供方（包括 Claude）不会被声明为原生图片生成器。聊天模型可以使用已配置的图片生成工具，由另一个已登录的提供方提供服务。订阅操作解析已存储的 OAuth 授权并保留提供方拥有的元数据；它们不会回退到单独计费的 API 凭据。

## 考虑过的替代方案

**添加新的核心媒体协议或修改 agent loop。** 现有图片块、工具结果、附件授权和紧凑流记录已能表示所需的持久化事实。并行协议会重复这些职责归属，并增加上游合并风险。

**将图片 URL 或 base64 作为文本返回。** 文本不提供持久化图片准入、授权检索或一致的图库展示。远程 URL 过期时，图片还可能丢失；嵌入字节则会扩大历史。

**使用原生原始签名回放规范化字节。** 规范化可能改变方向、元数据、尺寸或编码。不能假定原始提供方部分的签名也授权了这些改变后的字节。

**发送任意文件字节而不是 Harness 文件句柄。** 这会改变每个适配器已确立的输入约定，并绕过执行文件系统的只读访问映射。原生 auth2api 文档端点继续与 Harness 请求组装分离。

## 影响

提供方实现和配置决定可用的图片生成模型。共享 agent loop、已发布的 Session 代际、SDK 协议和上游默认组合包保持不变。持久化原件与规范化预览可能占用不同的不可变对象，遵循附件后端现有的保留策略。图片生成请求可能消耗订阅额度；结果不明确的失败不得静默触发另一个提供方或 API 密钥回退。

[嵌入式流读取器决定](../architecture/2026-09-06-embedded-stream-record-readers.zh.md)继续约束图片查找和流投影。本说明为输入图片决定扩展输出职责归属；它不取代其规范化、请求大小或远程文件策略。

## 验证

聚焦的提供方测试覆盖生成图片准入、格式错误和超限输出、取消、顺序及回放。原生运行时测试覆盖全部四个路由名称的文件句柄投影和结构化图片输入。手工编写的 `subscription-image-output` 无界面场景先通过 `read_image` 导入真实 PNG，再将其引用保留在助手内容和紧凑流记录中；它是持久化 Harness 行为的证据，不能代替真实提供方图片生成测试。
