# Agent Note: Local Claude and Codex plugin compatibility scanning

Status: implemented

English | [中文](2026-09-25-local-plugin-compatibility-scan.zh.md)

## Problem

Local Claude Code and Codex plugins contain executable hooks, MCP configuration, skills, and components that cannot be treated as a trusted package during import. fi already has the pieces an imported plugin's contributions would run on — `dsh-skill`'s provider seam (with `dsh-skill-filesystem` already able to load a directory of Claude-shaped `SKILL.md` files), `dsh-mcp-client`'s stdio/HTTP server bridge, and `dsh-hooks-claude-code`/`dsh-hooks-codex`'s single-`configPath` command-hook bridges — but none of them discover a plugin's own manifest layout, and nothing translates a Claude or Codex MCP server declaration into `dsh-mcp-client`'s config shape. The importer needs a complete inventory, explicit unsupported diagnostics, path containment, bounded reads, and a revalidation fingerprint without executing plugin content or changing the source tree, and every activation needs to be a decision a person made, not a decision the scan makes for them.

## Decision

The plugin compatibility scanner (`packages/extensions/plugin-compat/src/manifest.ts`) reads a local Claude or Codex plugin root and returns supported skills, MCP servers, command hooks, unsupported components, diagnostics, UTF-8-decoded source text, and a deterministic fingerprint over exact source bytes. It accepts Claude's default `skills/`, `hooks/hooks.json`, and `.mcp.json` layout without `plugin.json` when that layout is present; Codex imports require `.codex-plugin/plugin.json`. An ambiguous root with both manifests is rejected.

The scanner parses skill frontmatter with the `yaml` package fi already depends on for `dsh-skill-filesystem`, validates MCP stdio and HTTP entries, validates the supported hook event and command subset, and records unsupported events, hook types, async hooks, components, and malformed values instead of silently dropping them. It substitutes only the documented plugin and trusted activation directory placeholders. It never executes commands, scripts, agents, applications, LSP configuration, or MCP servers.

The scanner applies configurable entry-count (`maxEntries`), file-count, per-file, and aggregate byte limits before reads. Every source path passes lexical and realpath containment checks, including manifest parents and default configuration paths. The fingerprint hashes exact bytes for the manifest, discovered skill files and resources, and discovered MCP or hook configuration; retained source text is decoded as UTF-8 for parsing. Activation re-scans the same local root so added or deleted relevant contributions are detected; the fingerprint does not attest to hook scripts or transitive dependencies that were not discovered as plugin source files.

`PluginCompatService` (`packages/extensions/plugin-compat/src/index.ts`) owns one durable global document plus canonical-workspace records; importing never reads repository configuration or executes a plugin's local settings. Explicit item enablement is required for MCP and hooks — an imported skill is enabled by default because it is inert text until a model chooses to load it, while an imported MCP server or hook can run a local command or reach a network server as soon as a session composes, so those start disabled. Mutations serialize through one queue; disposal waits for the active mutation and rejects queued work before closing.

`agent/created` — the current, awaited-serial equivalent of the extension point an earlier divergent line of this feature called `agent/setup` — is the lifecycle seam for this composition (`packages/extensions/plugin-compat/src/runtime.ts`'s `mountManagedPlugins`, called from `PluginCompatService`'s constructor). Plugin mounting completes before agent publication, and initialization failure rolls back creation, matching `docs/architecture.md`'s turn-flow contract. This keeps the feature out of the agent loop and preserves the existing native hook bridge behavior, including its detached SessionStart timing and unsupported output controls. Each contribution mounts as a child plugin on the composing agent's own `agent.ctx` (an agent-scoped context whose contributions unwind on that agent's disposal, the same primitive `dsh-browser-use-runtime`'s per-agent MCP mounting already uses), so a resolved skill, MCP server, or hook set never outlives the agent it was resolved for.

Rollback-after-settlement alone only interrupts work that settles on its own; an MCP server's connection attempt has no natural deadline, so an unresponsive one would hang `agent/created` and the whole `ctx.agents.create()` call rather than reject on cancellation. `mountManagedPlugins` therefore takes an optional `signal`, threaded from `agent/created`'s own payload, and a `mountCancelable()` helper disposes the pending MCP-client Fiber as soon as that signal aborts, preferring the signal's own abort reason over whatever the disposed Fiber's `await()` settled with — the same idiom `dsh-browser-use-runtime`'s per-agent MCP mount already uses. Skill and hook mounting need no such signal: both are bounded local work already covered by ordinary rollback-after-settlement, confirmed by dedicated hook-directory-creation and hook-config-write cancellation tests.

Selected hook rows materialize their generated configuration in a private temporary directory, written with mode `0o600`, and mounted through the unmodified `dsh-hooks-claude-code`/`dsh-hooks-codex` bridges — the same command-hook runner and typed-decision mapping an unmodified deployment already uses. Selected MCP servers mount through the unmodified `dsh-mcp-client`, translating a discovered `command`/`args`/`env`/`cwd` or `url`/`headers` shape into its `StdioConfig`/`StreamableHttpConfig`. Selected skills call `dsh-skill`'s `ctx.skills.register()` directly, tagged with a `claude-plugin`/`codex-plugin` `SkillSource` and the owning plugin's id in metadata.

No package-owned `./invariant` companion is published. `packages/AGENTS.md`'s invariant rule now rejects an installer whose only content is an empty check or a fixed-example probe; this package's durable state is already covered by its persisted document's `zod` schema (rejected at read time) and by the per-activation fingerprint re-check (rejected at mount time), so a separate companion would only wrap an existing check rather than report an independently diverging observation. The rationale lives in this package's README instead, per the same rule.

The only shipped consent surface is five `dsh-commands` registrations (`/plugin-import`, `/plugin-list`, `/plugin-enable`, `/plugin-disable`, `/plugin-remove`) at global scope, rather than a browser Settings surface. `PluginCompatService`'s public methods, including workspace-scoped selection and per-item override reset, are unchanged from the capability an equivalent settings card would need, so a future card can drive them directly; only the shipped UI is reduced from the two-scope, override-aware card an earlier divergent line of this feature built.

## Alternatives considered

- **Trust the plugin manifest and execute declared entries** — rejected because local plugin content is executable code and import must remain an inspection operation.
- **Scan every file under the plugin root** — rejected because package caches and unrelated files make the scan unbounded and expand the trust surface beyond declared plugin components.
- **Silently omit unsupported components** — rejected because a consumer of the inventory would see an incomplete picture, and activation could claim support that does not exist.
- **Ship a browser Settings surface in this change** — deferred. `dsh-commands` already provides a documented, tested extension point for a human-triggered mutation, and building it first keeps every security property (bounded scan, path containment, no execution, per-item default-off consent, fingerprint revalidation) reviewable independent of client UI scope; a settings card is unblocked future work against the same `PluginCompatService` methods.
- **Publish a no-op `./invariant` companion, matching the earlier divergent line** — rejected: the tightened invariant rule (`packages/AGENTS.md`) now treats an installer with no independently diverging observation as invalid, and this package's two existing checks (document schema, fingerprint re-check) already cover the state a companion would otherwise reserve ownership over.

## Consequences

Valid plugins can import with warnings for unsupported entries, while malformed supported entries and unsafe paths fail closed. Default and manifest-declared Claude skills are additive. The source tree remains unchanged, and the inventory retains exact bytes for relevant files. Script and dependency integrity remains outside this fingerprint and requires a later execution-integrity design.

The first release is local-only: marketplace resolution and full vendor emulation remain outside this package. A skill that declares execution restrictions the Harness cannot map remains visible as unsupported and is never registered as an ordinary runnable skill. Selecting an MCP server or hook to enable is a deliberate act through a command, never a side effect of importing or listing a plugin.
