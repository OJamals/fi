# Agent Note: fi first run without a DeepSeek account

Status: implemented

English | [中文](2026-09-25-fi-first-run-without-deepseek-account.zh.md)

## Problem

fi is a model-universal product built on the vendored DeepSeek Harness (DSH) runtime, but its first launch still ran DSH's own onboarding: the packaged Desktop app opened a native welcome window (`apps/desktop/src/welcome-window.ts`) that gated the workspace behind a DeepSeek-account sign-in or a DeepSeek API key (`welcome-api.ts`'s `needsWelcome`), and, once past it, the embedded workspace still mounted DSH's DeepSeek-account settings UI (`packages/client/ui-settings-account`) and its Remote (`packages/api/account-controller`) — an account menu, a quota notice, a Models-page sign-in slot, and a desktop-onboarding overlay, all specific to a DeepSeek Platform account fi does not offer. A user who is not a DeepSeek Platform customer could not get past first run at all.

The generic Web onboarding step already exists and is model-universal: `packages/client/ui-settings-models`'s `ModelSetupDialog` routes an unconfigured user to the Models page instead of collecting any one vendor's credential. It never ran inside Desktop, though, because its automatic-show condition assumed any shell exposing the `dshDesktop` global already owned first-run onboarding — true for DSH's own Desktop, false for fi's once the DeepSeek gate above is turned off.

## Decision

`needsWelcome` (`apps/desktop/src/welcome-api.ts`) is hardwired to `false` behind a documented `FI_NATIVE_WELCOME_DISABLED` constant: fi's Desktop goes straight from Host startup to the workspace, on every code path that used to ask whether to show the native welcome window. The window's implementation (`welcome-window.ts`, `welcome-backend.ts`, `preload-welcome.ts`, its renderer) stays in the tree — `needsWelcome` is its only caller-facing gate, and every consumer already funnels through it — but registers no IPC and shows no window while the constant holds. `main.ts`'s Host-start handler no longer subscribes to DeepSeek account state (`accountBackend.watch(...)`): that subscription only existed to reopen the welcome window on sign-out or session expiry, both unreachable once the gate is off, and its Remote (`account-controller`) is unmounted in fi's own bundle (below), so leaving the subscription running would poll a namespace that no longer resolves. `welcome-backend.ts`'s `read()` — still used for the one thing that survives the gate, resolving the saved locale preference at startup and the `dsh-desktop:onboarding-api-key` IPC probe — no longer awaits `account.state()` for its `loggedIn` field, which fi never reads: it returns `false` outright.

`packages/fi/authorization-bundle/cordis.patch.yml` — the last bundle layer applied to both the `web` and `desktop` profiles (`PROFILE_TEMPLATES.web` in `packages/boot/app-boot/src/profile.ts`; `DESKTOP_PROFILE_BUNDLES` in `apps/desktop/src/desktop-profile.ts`) — disables four rows the upstream `base`/`web-app` bundles mount: `ui-settings-account` and `account-controller` (the DeepSeek-account settings UI and its Remote), and `deepseek-account` and `llm-deepseek-account` (the Host account service and its account-based LLM route). This is the same mechanism the file already used to disable `web-search-deepseek`, and it changes nothing in the upstream bundle files themselves. `llm-deepseek` (the API-key route) is untouched, so DeepSeek stays selectable as an ordinary provider through a user-supplied key on the Models page. `deepseek-account`'s removal also silences the native "Platform" webview plumbing (`apps/desktop/src/platform-view.ts`, the Host's `'platform-session'` IPC event) that only `ui-settings-account`'s recharge/top-up pages ever opened; with that plugin gone, nothing calls it — the same steady state Linux Desktop already runs in today, since `deepseek-account`'s `desktopPlatform` config already evaluates to `null` off macOS/Windows.

`packages/client/ui-settings-models`'s `automaticModelSetup` no longer excludes `dshDesktop`; it is exactly `configured.credentialOnboarding`. The package's internal-testing `WelcomeNotice` step keeps its Web-only exclusion (`!('dshDesktop' in globalThis)`), an unrelated, unchanged choice. `ModelSetupDialog` is therefore fi's one first-run credential step everywhere: Web and Desktop behave identically.

Remaining user-visible "DeepSeek Harness" copy was swept and fixed where the surface is live in fi's build: `apps/desktop/src/locale.ts`'s `welcome*` strings (unreachable in normal operation now, fixed anyway since the native window stays in the tree), `ui-plugin-manager`'s plugin-install safety copy, and `ui-sidebar-documentpreview`'s Office-unavailable copy, in both `en` and `zh`. `ui-settings-account`'s own copy was left as upstream DSH text: the package is fully disabled in fi and editing a disabled package's strings would only create merge friction against the vendored source it still resembles. The packaged app's window/document title already reads "fi" without a change here — `scripts/client-build-environment.ts`'s `OFFICIAL_CLIENT_BUILD_ENVIRONMENT` already sets `DSH_CLIENT_TITLE: 'fi'`, and `apps/desktop/scripts/package-target.ts` already builds through `pnpm run build:official`; the literal "DSH Local Build" fallback text remains correct as a non-official/local-dev-build label.

### Model-visible DSH/fi runtime clarification

Separately, the fixed `harness:identity` opener in `packages/core/system-prompt/src/index.ts` gained one sentence directly after `You are an AI agent powered by fi.`: its tools, skills, `DSH_*` environment variables, `dsh` CLI, and `@deepseek-ai/dsh-*` package names still name DeepSeek Harness while only the opener said fi, and users reported the in-app agent treating DSH as a separate product and searching for a nonexistent "DSH source repo" or `$DSH_HOME/.agent-presets`. The added sentence states that `dsh`, `DSH_*` variables, and `@deepseek-ai/dsh-*` packages are fi's own runtime, not a separate product or checkout, and that `$DSH_HOME` is fi's data home; `editing-cordis-compositions`'s `SKILL.md` also gained a one-clause guard so its "Migrate a legacy preset" section stops steering the model to inspect that same directory when it does not exist. Every `system-prompt.expected.md` and the one affected `.jsonl` fixture that pins the rendered prompt or that `SKILL.md` body were hand-edited to match rather than re-recorded, since `test:snapshot:record` needs a live-model API key this environment lacks and would rewrite unrelated recorded content.

This sits beside, and does not reverse, [fi agent self-identification](2026-09-10-fi-agent-self-identification.md)'s rejection of "naming the implementation in the opener": that note kept the fixed identity sentence itself free of implementation branding, and it is still exactly `You are an AI agent powered by fi.`, byte-identical. The new sentence is a second, separate one addressing a different problem — a model that already knows it is fi still needs to resolve concrete tool-visible strings (`dsh`, `DSH_*`, `@deepseek-ai/dsh-*`) it will otherwise treat as evidence of a second product — not the identity the model states about itself.

## Alternatives considered

**Delete the native welcome window subsystem outright** instead of gating it. Rejected: `welcome-backend.ts`'s `read()`/`readLocalePreference()` also serves the startup locale-preference read and the `dsh-desktop:onboarding-api-key` IPC probe, unrelated to the DeepSeek gate; a full removal would have to re-home that logic elsewhere for no behavioral gain over hardwiring the one decision function that already governs every call site.

**Keep `needsWelcome`'s real boolean logic and gate its three call sites in `main.ts` individually.** Rejected: the account-state watch that reopens the window on sign-out/session-expiry is not conditioned on `needsWelcome` at all — it runs unconditionally once the Host starts — so gating only the `needsWelcome` call sites would leave that subscription polling a Remote namespace fi has disabled. The fix has to touch both, and hardwiring the single decision function is the smaller, single-source change once the watch itself is removed.

**Disable `deepseek-account`/`account-controller` by editing `packages/bundle/base`/`packages/bundle/web-app` directly.** Rejected per this repository's own convention: those bundles stay mergeable against the upstream DeepSeek Harness composition; fi's product differences live in `packages/fi/authorization-bundle`'s patch layer, which already disables `web-search-deepseek` the same way and composes last in both the `web` and `desktop` profiles.

**Gate `ModelSetupDialog`'s automatic show behind a new explicit Host config flag instead of dropping the `dshDesktop` check.** Considered, but Desktop's embedded browser and a plain Web deployment share the identical `base`+`web-app` Host composition and Remote surface — there is no Host-side signal available at boot time that distinguishes "this Host serves a Desktop webview" from "this Host serves a browser tab" for a value baked once into `webserver/index-inject`. Only the client-side `dshDesktop` global reliably knows this, and since fi retired the only reason to treat Desktop differently, removing the special case is exact.

## Consequences

fi's Desktop reaches the workspace on every launch without a DeepSeek-account or API-key prompt; `ModelSetupDialog` is the one first-run credential step, consistent between Web and Desktop. No DeepSeek-account UI, sign-in flow, quota notice, or bonus notice renders anywhere in fi's assembled Web or Desktop app; DeepSeek itself remains configurable as an ordinary API-key provider. The retired native welcome window's IPC, renderer, and tests stay in the tree as inert infrastructure `needsWelcome` never invokes — a future product that wants a native DeepSeek-account gate again can flip `FI_NATIVE_WELCOME_DISABLED` back, though its `WELCOME_IPC.state` live-update wiring (removed from `main.ts`'s account watch) and the quit-confirmation cancel path's welcome re-show (`main.ts`, `before-quit`) would need re-verification first, since neither was exercised by this change. `deepseek-account`'s native Platform webview (top-up/recharge pages) is unavailable in fi, matching Linux Desktop's existing behavior on every platform.
